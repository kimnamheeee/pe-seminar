# 하차 정류장 매핑 후속 검토

## 목적

가는김에는 대중교통 경로와 식당을 따로 찾아 비교하느라 길찾기를 멈춰야 하는 불편을 줄이려는 서비스다. 경로 주변 식당만 보여주고 그 식당에 가려면 어느 정류장에서 내려야 하는지 알려주지 않으면, 사용자는 하차 지점을 다시 별도로 검색해야 한다. 식당을 찾는 수고는 줄어도 처음 해결하려던 불편이 반복되므로 문제를 충분히 해결했다고 보기 어렵다. 따라서 식당에 들르기 좋은 하차 정류장 안내는 부가 기능이 아니라 문제 해결을 완성하는 핵심 기능이다.

아래 검토는 이 기능을 넣을지 판단하기 위한 것이 아니라, 구현에 쓸 정류장 좌표와 매핑 방식이 실제로 작동하는지 확인하기 위한 것이다.

## 현재 확인된 점

- 기존 Kakao 대중교통 경로 응답 샘플에서 정류장 13개는 이름만 포함하고 좌표와 ID는 제공하지 않았다 ([핵심 검증 샘플](samples/current-core-validation.json)).
- 좌표를 얻기 위해 [TMAP 대중교통 API](https://transit.tmapmobility.com/docs/routes)로 전환하는 방안을 검토했다. 하지만 무료 요금제의 대중교통 경로 API 한도가 하루 10회라, 사용자의 길찾기 요청마다 API를 호출하는 방식은 한도에 걸릴 수 있다고 판단해 TMAP을 선정하지 않았다 ([요금제 안내](https://transit.tmapmobility.com/)).
- 정류소 위치정보는 경로 탐색 결과처럼 매 요청마다 최신 조회가 필요한 값은 아니므로, 요청 때마다 외부 API를 호출하는 대신 정적인 공개 데이터를 DB에 넣어 조회하는 방안을 검토한다. 공개 정류소 데이터가 자주 바뀌지 않는다는 전제와 갱신 요건은 실제 운영 전에 확인한다.
- 후보 데이터로 [서울시 버스정류소 위치정보](https://data.seoul.go.kr/dataList/OA-15067/A/1/datasetView.do)를 발견했다. 버스 정류소 좌표와 정류소 ID를 제공하며, 정류소 이름은 중복될 수 있으므로 이름만으로 레코드를 고유하게 식별할 수 없다.
- 이번 검토는 같은 이름의 정류소가 여러 곳에 있어 경로 기준으로 후보를 구분해야 하는 버스 정류소 문제에 집중한다. 지하철역은 역명이 고유해 같은 이름 후보를 경로로 구분하는 동일한 문제가 없으므로 이번 데이터 매핑 검토 범위에 포함하지 않는다.

`data/seoul-bus.xlsx`를 확인했다. 시트에는 11,236개 행과 `NODE_ID`, `ARS_ID`, `정류소명`, `X좌표`, `Y좌표`, `정류소타입` 컬럼이 있다. 이 중 8개는 `한강선착장`이고, 나머지 11,228개는 버스 정류소 유형이다. 버스 정류소 이름은 7,375종이며, 그중 3,130개 이름이 둘 이상의 행에 나타난다. `낙성대입구`는 7개 레코드로 나뉘어 있다. 따라서 이름 검색은 후보군을 좁히는 단계로만 쓰고 좌표와 경로를 사람이 대조할 필요가 있다.

서울 밖으로 나가는 경로는 서울 정류소 데이터로 전체 정류장을 보강할 수 없으므로 서울 표본으로 사용하지 않는다. 표본 수집 스크립트와 검토 데모는 경로 형상 전체가 서울 경계 안에 있는 경우만 통과시킨다. 현재 경계 파일은 [서울 자치구 경계 GeoJSON (2017)](https://github.com/datainworld/administrative_district/tree/master/3_%EC%84%9C%EC%9A%B8%EC%8B%9C_%EC%9E%90%EC%B9%98%EA%B5%AC)이며 `data/boundaries/seoul-districts-2017.geojson`에 둔다. 운영에 쓰기 전 최신 공식 경계로 교체해야 한다.

데모 화면에 나온 예시 이름을 대조했을 때 `금천패션아울렛사거리.마리오`는 2개, `디지털3단지사거리`는 3개의 정확한 버스 정류소 레코드가 있다. 이들이 0개 후보로 보인다면 정류소 XLSX가 데모에 로드되지 않았거나 파싱되지 않은 상태다. 반면 `광명성애병원`, `광명경찰서`, `철산센트럴푸르지오`는 서울시 데이터에서 찾지 못했다. `성애병원`이라는 별도 이름의 정류소는 있지만, 이름 일부만 같다는 이유로 같은 정류소로 매핑하면 안 된다. 서울시 데이터만으로는 행정구역 경계를 넘어가는 버스 경로의 모든 정류소를 보강하지 못할 수 있다.

## 검토 결과와 잠정 결론

사람이 먼저 경로 약 15개를 살펴봤다. 지금까지는 전반적으로 잘 맞아 보였고, 이름이 비슷해 중복 후보가 생기는 정류소들도 좌표 간 거리가 대체로 멀지 않다는 관찰이 있었다. 전체 경로를 모두 검토할 시간은 부족하므로, 정량 평가는 나중에 진행하기로 했다.

2026-11-08 KST 내보내기 파일 `data/stop-mapping-review.json`의 버스 정류장 항목을 계산한 후보 커버리지는 **7,286개 중 6,643개(91.17%)**다. 이 수치는 이름 기준 후보가 하나 이상 검색된 비율이며, 후보가 여러 개여도 매핑된 것으로 센다. 정답을 맞힌 비율이나 경로별 성공률은 아니다. 따라서 현재 결과는 서울시 데이터와 최근접 후보 규칙을 사용해 볼 만하다는 잠정 판단의 근거로 삼되, 실제 정답률을 검증한 결과로 해석하지 않는다.

1. 정류소 이름을 정규화해 서울시 버스정류소 데이터에서 후보를 찾는다. 이름은 검색 조건으로만 쓰고 고유 키로 사용하지 않는다.
2. 해당 버스 구간의 경로 형상에서 후보 좌표까지의 거리를 계산하고, 가장 가까운 후보를 해당 경로의 정류소로 선택한다. 후보가 동률에 가깝다면 경로상 순서를 보조 기준으로 쓴다.
3. 서울 경계를 벗어나거나 경로 형상을 확인할 수 없는 경로는 하차 정류장 안내를 제공하지 않는다. 경로 검색과 식당 표시는 유지한다.

현재 이름 대조 규칙만으로도 후보 커버리지가 90%를 넘으므로, 초기 구현은 이 규칙으로 진행해도 될 것으로 판단했다. 괄호 안 승강장·중앙차로 표기나 슬래시 별칭을 추가로 정규화하는 일은 당장 필요한 작업으로 보지 않고 후속 작업으로 미룬다. 이런 표기를 무조건 제거하거나 나누면 서로 다른 정류소를 잘못 합칠 수 있으므로, 실제 사례별 휴먼 검토를 거쳐 규칙을 정해야 한다.

이 방식은 사람이 확인한 초반 경로의 정성적 인상과 현재 후보 커버리지를 바탕으로 한 잠정 구현 방향이다. 전체 정답률과 거리 임계값은 아직 확인하거나 정하지 않았다. 서비스 적용 후 오매칭 사례를 수집할 수 있도록 선택된 데이터셋 ID와 경로까지의 거리를 추적하는 방안을 구현 시 검토한다.

## 측정 범위와 방법

이번 수치는 무작위 경로의 평균 매핑률을 추정하거나, 중복 정류소가 가장 많이 들어 있는 경로를 역으로 찾아내려는 것이 아니다. 실제 경로를 살펴보며 후보가 검색되는 정도를 확인하는 탐색적 계산이다.

요약은 `data/stop-mapping-review.json`의 항목 중 `mode == "BUS"`인 행만 사용했다. 분모는 버스 구간에서 나온 정류장 항목 수이고, 현재 데모의 이름 정규화 규칙을 적용한 뒤 `candidateCount >= 1`이면 후보가 잡힌 것으로 계산했다. 현재 규칙은 공백과 일부 문장부호만 제거하고 나머지 글자는 같아야 한다. 도보 항목은 분모에서 제외했고, 복수 후보도 매핑된 항목으로 센다.

현재 파일에서 산출한 요약은 다음과 같다. 도보 구간은 제외하고 `mode`가 `BUS`인 항목만 계산했다. 매핑은 `candidateCount >= 1`로 정의한다.

| 지표 | 결과 |
|---|---:|
| 경로 수 | 275 |
| 버스 정류장 항목 | 7,286 |
| 후보 1개 이상 | 6,643 (91.17%) |
| 후보 0개 | 643 (8.83%) |
| 복수 후보 | 4,333 (59.47%) |

이 비율은 내보낸 검토 파일에 들어 있는 항목의 **현재 이름 매칭 규칙 기준 후보 커버리지**이며, 대표 표본에서 계산한 수치가 아니고 사람이 정답 여부를 모두 확인한 결과도 아니다. 파일의 BUS 항목 중 126개는 O, 7,160개는 검토 대기 상태다. 따라서 91.17%를 정답률이나 Kakao 지도 검색 가능률로 읽으면 안 된다. 전체 정답률은 나중에 사람이 더 많은 경로를 검토하고 O/X 판정을 집계한 뒤 계산한다.

`후보 없음`은 정류장이 실제로 없거나 Kakao 지도에서 검색되지 않는다는 뜻이 아니다. 현재 방식이 Kakao 경로 응답 이름을 서울시 정류소 데이터의 이름과 바로 대조했을 때 같은 이름 후보를 만들지 못했다는 뜻이다. 예를 들어 경로 응답 `동대문구청(중)`은 서울시 데이터의 `동대문구청`과 일치하지 않지만, `(중)` 표기를 떼면 데이터에서 후보가 나온다. `청량리역환승센터(4번승강장)`도 괄호 정보를 떼면 여러 정류소 후보를 찾을 수 있다. `A/B`처럼 Kakao가 두 표기를 합쳐 반환한 이름도 데이터 이름 하나와 바로 일치하지 않을 수 있다. 괄호의 모든 내용을 없애거나 `/`로 무조건 나누는 방식은 승강장·방향 구분을 잃을 수 있으므로, 이 변형 후보들은 경로 좌표로 다시 대조해야 한다. 초기 탐색에서 괄호 내용을 제거하고 슬래시 이름을 나누는 단순 규칙을 적용하면 현재 후보 없음 643건 중 320건에서 데이터 후보를 추가로 찾을 수 있었지만, 이는 정답 검증 전의 참고값이지 매핑 성공으로 집계하지 않는다.

## 사람 검토 데모

`tools/stop-review/index.html`에 표본별 검토 데모를 둔다. Kakao 길찾기 원본 응답 JSON, `data/seoul-bus.xlsx`, 서울 경계 GeoJSON을 불러오면 서울 경계 안의 순수 버스 경로만 선으로 그리고 이름이 일치하는 서울 버스 정류소 후보를 핀으로 표시한다. 경계 데이터가 로드되지 않으면 경로를 표시하지 않는다. 데모는 정류소 유형이 `일반차로`, `마을버스`, `중앙차로`, `가로변시간`, `가로변전일`인 행만 사용하고 선착장 등 다른 유형은 제외한다. 각 응답의 서울 내 버스 경로 선택지를 보여주며, 중복 이름 후보 수는 관찰을 돕는 참고 정보로 표시한다.

각 정류소 이름에 후보가 있으면 해당 버스 구간 경로선까지의 거리가 가장 가까운 후보 하나를 기본 제안으로 표시한다. 이번 검토를 바탕으로 이 최근접 규칙을 서비스 구현의 기본 매칭 방식으로 삼는다. 데모에서는 사람이 제안의 정답 여부를 O/X로 검토하고, X이면 다른 후보나 후보 없음으로 수정할 수 있다. O/X와 선택한 정답 ID는 브라우저 로컬 저장소에 보관하고, JSON 내보내기에 제안 ID·제안 거리·검토 판정·정답 ID를 포함한다.

추가 표본을 수집할 때는 먼저 `python3 scripts/capture-stop-review-samples.py --count 50`으로 좌표쌍을 미리 보고, 호출이 필요하다고 결정한 뒤 `--execute`를 지정한다. Kakao 키는 루트 `.env`의 `KAKAO_REST_API_KEY` 또는 환경변수에서 읽고, 응답은 `data/stop-review-responses.json`에 저장한다. 기존 출력 파일을 바꾸려면 `--force`를 지정한다.

데모는 저장소 루트에서 `python3 -m http.server 8000`을 실행한 뒤 `http://localhost:8000/tools/stop-review/`에서 열 수 있다. `data/stop-review-responses.json`과 `data/seoul-bus.xlsx`를 불러와 O/X를 검토하고 JSON으로 내보낸다. 지도 타일과 브라우저 라이브러리를 불러오려면 인터넷 연결이 필요하다.

## 데이터 운영 요건

서울시 데이터셋을 채택하면 1만 건이 넘는 정류소 레코드를 앱에 싣지 않고 DB에 적재해 서버에서 조회한다. 서울시 정류소 ID를 레코드 식별자로 보존하고 정류소 이름은 고유하다고 가정하지 않는다.

데이터 제공처에서 새 파일이 공개될 때 DB를 갱신할 수 있어야 한다. 갱신은 새 버전을 반영한 뒤 기존 데이터와 교체하는 흐름을 기본 방향으로 검토하며, 실제 적재 도구와 갱신 주기는 검증 결과와 배포 운영 방식에 맞춰 결정한다.

## 다음 구현 과제

매칭 방식은 현재 데모의 최근접 후보 규칙으로 정하고, 다음은 구현 단계에서 다룬다.

1. 서울시 버스정류소 데이터의 DB 적재·조회와 새 데이터 공개 시 갱신 절차
2. 서울 경계 파일의 최신 공식 데이터 교체 및 갱신 절차
3. 매칭 결과의 거리와 선택된 정류소 ID를 기록해 이후 오매칭을 점검할 방법
4. 정규화 누락 후보 사례를 모아 괄호 표기와 슬래시 별칭을 휴먼 검토하고, 안전한 이름 변형 규칙을 정하는 후속 작업
