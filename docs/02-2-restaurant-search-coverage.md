# 경로 주변 식당 검색 범위 후속 검토

## 배경

서울역–강남역 예시에서 식당 후보가 15개만 나온 것을 두고, 긴 경로 주변을 탐색하기에는 결과가 적지 않겠느냐는 피드백이 있었다. 우선 현재 Kakao Local API 요청이 실제로 어떤 범위와 페이지 조건을 사용하는지 다시 확인했다.

## 현재 확인된 요청

검증 스크립트 [`verify-core-flow.mjs`](../scripts/verify-core-flow.mjs)는 60분 미만 첫 경로를 선택한 뒤, 경로 형상 전체의 최소·최대 경도와 위도를 구해 경로의 바깥 사각형을 만든다. 이 사각형을 동서남북 각 방향으로 1km씩 확장해 Kakao Local 음식점 카테고리(`FD6`) 검색에 전달한다.

현재 요청 파라미터는 다음과 같다.

- `rect`: 경로 전체를 감싼 경계 사각형 + 사방 1km 여유
- `category_group_code=FD6`
- `size=15`
- `page=1`
- `sort=accuracy`

이 조건으로 **한 번만** 요청한다. 따라서 현재 받은 15개는 큰 경로 사각형 안에서 정확도순으로 고른 첫 페이지다. 검증 응답의 `total_count`는 16,858, `pageable_count`는 45였고, 첫 페이지 15개 중 경로선에서 1km 이내인 곳은 5개였다. `verify-core-flow.mjs`는 이 15개를 경로까지의 거리순으로 정렬해 기록하지만, 스크립트 안에서 1km 밖 후보를 제거하지는 않는다. 설계상 앱에 전달할 후보에는 별도 1km 직선거리 필터를 적용하는 것으로 적혀 있다.

카카오 카테고리 검색은 한 페이지에 최대 15개를 반환한다. 페이지를 바꾸어 추가 결과를 받을 수 있고, `pageable_count`는 검색 결과 중 노출 가능한 문서 수로 최대 45개다. 따라서 이 예시에서는 같은 검색 범위에서 2·3페이지를 요청해 최대 45개까지 받아볼 수 있다. [Kakao Local API 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide)

## 1차: 동일 사각형에서 페이지네이션

우선 검색 사각형은 그대로 두고, `page=1`부터 응답의 `is_end`가 참이 될 때까지 페이지를 순서대로 요청한다. 각 페이지 크기는 허용 최대인 15로 두고, 응답들을 합칠 때 Kakao 장소 ID로 중복을 제거한다. 그다음 경로선까지의 직선거리를 계산해 1km 이내 후보를 추린다.

서울역–강남역 예시에서 다음을 비교한다.

- 첫 페이지 15개 중 경로선 1km 이내 식당 수
- 페이지네이션 후 전체 결과 중 경로선 1km 이내 식당 수
- 중복 제거 전후 결과 수와 경로를 따라 후보가 분포하는 모습

검증 스크립트 [`verify-core-flow.mjs`](../scripts/verify-core-flow.mjs)는 `is_end` 또는 `pageable_count`에 도달할 때까지 페이지를 순회하고, 장소 ID로 중복을 제거한다. 2026-11-08 KST 실행에서 페이지네이션으로 아래 결과를 확인했다. 앱의 실제 `searchRestaurants` 기능은 아직 구현되지 않았다.

### 페이지네이션 실행 결과

- 서울역→강남역의 기존 선택 경로와 검색 사각형을 사용했다. 이번 실행에서 선택된 경로 유형은 `SUBWAY`였다.
- `page=1, 2, 3`을 순회해 총 45개를 받았다. 장소 ID 중복은 0개였다.
- 응답 메타는 `total_count=16,850`, `pageable_count=45`였다. 45개 중 경로선에서 1km 이내인 식당은 18개, 1km 밖은 27개였다.
- 기존 단일 페이지 검증에서는 15개 중 5개가 1km 이내였다. 페이지네이션 실행 후 근접 후보는 5개에서 18개로 늘었다. 다만 Kakao 데이터가 조회 시점에 따라 바뀔 수 있고 이전 응답의 `total_count`(16,858)와 이번 응답(16,850)도 달라, 완전히 동일한 시점의 비교는 아니다.

같은 넓은 사각형에서 페이지를 순회하는 것만으로도 이 경로에서는 근접 후보가 증가했다. 다른 경로에서도 충분할지는 별도로 확인해야 한다.

## 2차: 1km 격자 검색 비교

페이지네이션 결과와 비교하기 위해 같은 경로 사각형 안에서 경로로부터 약 1km 이내를 덮는 1km × 1km 셀을 만들고, 각 셀에서 동일한 FD6 페이지네이션 검색을 수행했다. 구현은 경로선을 100m 간격으로 보간하고, 50m 여유를 두어 경로 주변 셀을 선택한다. 모든 셀 결과를 Kakao 장소 ID로 중복 제거하고, 전체 경로선까지의 거리를 다시 계산해 1km 이내 여부를 비교했다. 실행은 다음과 같이 했다.

```bash
node scripts/verify-core-flow.mjs --compare-grid
```

### 격자 실행 결과

- 경로 주변을 덮는 셀: 50개
- Local API 요청: 131회 (페이지네이션 방식은 3회)
- 셀 응답에서 받은 항목: 1,817개, ID 중복 제거 후 1,816개
- 경로선 1km 이내: 1,214개 (페이지네이션 방식은 18개)
- 페이지네이션 결과와 겹치지 않는 1km 이내 후보: 1,196개
- 50개 셀 중 40개가 각각 `pageable_count=45`에 도달해 노출 상한에 찼다. 이 셀들에는 더 많은 검색 결과가 있어도 이번 호출로는 가져오지 못했을 수 있다.

격자 검색은 이 경로에서 검색 원자료를 크게 늘렸지만, Local API 요청도 3회에서 131회로 늘었다. 그리고 대부분의 셀이 결과 상한에 도달해, 1,214개를 해당 영역의 전체 식당 수로 볼 수 없다. **1,214개는 사용자에게 보여줄 목록이 아니라 API에서 모은 원자료 후보 수이며, 후보 수가 많다는 것 자체가 사용자 가치나 검색 품질을 뜻하지 않는다.** 전체 상세 응답과 셀별 결과는 [비교 JSON](samples/current-restaurant-grid-comparison.json)에 저장했다. 이 한 경로의 비교 결과로는 격자 방식을 서비스에 적용할 근거가 부족하다.

이후 고도화 선택지로는 셀별 거리순 검색, 경로에 가까운 셀만 더 세밀하게 나누기, 경로 중간의 버스 정류장이나 역을 검색 기준점으로 쓰기 등이 있다. 하지만 먼저 사용자에게 보여줄 적정 후보 수와 정렬 기준을 정해야 한다. 검색량을 최대화하기보다 적은 호출로 경로를 따라 선택할 만한 식당을 충분히 제공하는 것이 목표다. 셀 크기 비교는 `sort=accuracy`를 유지했다. 거리순 정렬이나 중심점 반경 검색은 아직 비교하지 않았다.

## 격자 크기 비교

1km 셀은 이 경로에서 50개 셀, 131회 Local API 요청을 만들었고 경로 1km 이내 원자료 후보도 1,214개였다. 셀이 너무 촘촘해 호출이 많고, 검색 원자료도 사용자가 직접 탐색할 목록으로는 지나치게 많았다. 그래서 격자 한 변을 3km, 5km 등으로 키워 호출 수와 원자료 후보량이 사용하기 적당한 수준이 되는 지점을 찾아보기로 했다.

같은 경로와 검색 방식을 유지하고 셀 한 변의 길이를 바꿔 추가 비교했다. 각 셀은 응답 끝까지 페이지를 조회했고, Kakao 장소 ID를 기준으로 셀 간 중복을 제거했다. 아래의 후보 수는 사용자 화면에 보여줄 수가 아니라 검색에서 모은 원자료 중 경로선 1km 이내인 수다.

| 셀 한 변 | 셀 수 | Local API 요청 | 고유 원자료 후보 | 경로 1km 이내 | 상한에 찬 셀 |
|---:|---:|---:|---:|---:|---:|
| 1km | 50 | 131 | 1,816 | 1,214 | 40 / 50 |
| 2km | 17 | 51 | 764 | 385 | 17 / 17 |
| 3km | 9 | 27 | 405 | 209 | 9 / 9 |
| 4km | 5 | 15 | 225 | 119 | 5 / 5 |
| 5km | 4 | 12 | 180 | 103 | 4 / 4 |
| 6km | 3 | 9 | 135 | 68 | 3 / 3 |
| 8km | 2 | 6 | 90 | 36 | 2 / 2 |
| 10km | 2 | 6 | 90 | 32 | 2 / 2 |
| 12km | 1 | 3 | 45 | 18 | 1 / 1 |

페이지네이션만 적용한 큰 사각형 검색은 3회 요청으로 45개를 받아 18개가 경로선 1km 이내였다. 12km 셀은 이번 경로에서 사실상 이 큰 사각형 검색과 같았다. 5km 셀은 12회 요청으로 경로 1km 이내 후보 103개를 찾았다. 사용자는 5km가 MVP에 적당하다고 판단했으며, **MVP의 기본 격자 크기로 채택한다.** 1km보다 호출 수와 원자료 후보량을 줄이면서 검색·카테고리 필터에 쓸 후보 풀을 남기는 선택이다. 단, 5km 셀도 모두 노출 상한 45개에 찼고 실행 경로는 하나뿐이다. 5km는 검색 영역의 셀 크기이며 UI 표시 개수는 별도로 정한다.

2~12km 비교 결과는 [2·3·4·5km 실행 JSON](samples/current-restaurant-grid-size-sweep.json)과 [6·8·10·12km 실행 JSON](samples/current-restaurant-grid-size-sweep-6-8-10-12km.json)에 저장했다. API 데이터가 시점에 따라 달라질 수 있고, 모든 셀이 상한에 찼으므로 실제 전체 후보 수는 표의 값보다 많을 수 있다. 앱에는 이 원자료를 전부 노출하지 않고, 사용자에게 보여줄 목록 크기와 검색·카테고리 필터의 적용 범위를 별도로 정해야 한다.

## 현재 상태

- **기준 검색 방식:** 경로 전체 사각형을 사방 1km 확장해 `FD6`, `size=15`, `sort=accuracy`로 `is_end`까지 페이지 순회
- **1km 격자 기록:** 50셀·131회 호출 결과는 비교용으로 그대로 유지
- **검증 스크립트:** 동일 영역에서 `is_end` 또는 `pageable_count`까지 페이지네이션하고 장소 ID 중복 제거. 2026-11-08 실행 완료
- **MVP 격자 크기:** 5km 셀을 기본값으로 채택
- **아직 하지 않은 일:** 앱의 `searchRestaurants` 구현, 사용자에게 보여줄 적정 후보 수·정렬 기준 결정, 구현 후 실제 경로에서 품질 점검
